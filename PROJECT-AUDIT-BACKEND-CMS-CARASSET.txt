Migration yang sudah RAN (migrate:status):

   sessions
2) 0001_01_01_000001_create_cache_table — cache, cache_locks
3) 0001_01_01_000002_create_jobs_table — jobs, job_batches, failed_jobs
   (catatan: failed_jobs dibuat migration ini meski tidak selalu
   tercantum eksplisit di listing tabel)

PERNAH DIJALANKAN (users: 0 baris, diverifikasi via tinker read-only).

Tabel aktual di database (Schema::getTableListing()): cache, cache_locks,
failed_jobs, job_batches, jobs, migrations, password_reset_tokens,
sessions, users. TIDAK ADA data produksi/penting — database masih 100%
kosong dari sisi data (0 user, 0 baris konten apa pun). Aman untuk mulai
menambahkan migration CMS.

`media` dan `contact_messages` (lihat Tugas 11).

7. KONDISI AUTHENTICATION
======================================================================

Tidak terpasang: Laravel Breeze, Jetstream, Fortify, Laravel UI, Sanctum,
Passport, atau package role/permission (Spatie dsb.) — diverifikasi lewat
composer.json (hanya laravel/framework + laravel/tinker sebagai dependency
inti). Tidak ada middleware `auth`/`guest` custom terdaftar (folder
app/Http/Middleware belum ada), namun ALIAS bawaan Laravel 13
('auth', 'guest', 'throttle', dll.) tetap tersedia otomatis dari framework
tanpa perlu didaftarkan manual di bootstrap/app.php.

Jawaban poin audit:
1. Login sudah tersedia?               TIDAK.
2. Login publik dipertahankan/dihapus? Tidak ada login publik sama sekali
                                        saat ini — tidak relevan.
3. Bisa dipakai khusus admin?          Ya, guard `web` bawaan bisa dipakai
                                        untuk admin (satu tabel users,
                                        dibedakan lewat kolom `role`).
4. Route login lama berpotensi konflik? TIDAK ADA route login lama.
5. Guard default cukup?                Ya untuk fase pertama (1 role admin).
6. Perlu guard admin terpisah?         TIDAK perlu di fase pertama —
                                        cukup middleware `admin` di atas
                                        guard `web` bawaan, kolom `role`
                                        pada tabel users sudah memadai.
7. Satu tabel users cukup?             Ya, dengan tambahan kolom
                                        `role` (string/enum) dan
                                        `is_active` (boolean).
8. Kolom role & is_active diperlukan?  Ya, keduanya direkomendasikan.
9. Middleware admin diperlukan?        Ya (mis. `EnsureUserIsAdmin`).
10. Rate limiter login sudah ada?      Belum — perlu ditambahkan
                                        (Laravel menyediakan
                                        `RateLimiter`/`throttle` bawaan,
                                        tinggal dikonfigurasi).
11. Session driver aman?               `database` — aman, tabel `sessions`
                                        sudah tersedia dan sedang dipakai.
12. Password hashing sesuai Laravel?   Ya, `User::casts()` sudah
                                        mendeklarasikan `'password' =>
                                        'hashed'` (Laravel otomatis hash
                                        saat assignment).
13. Reset password dibutuhkan fase awal? TIDAK wajib fase pertama (jumlah
                                        admin diperkirakan sangat sedikit;
                                        bisa direset manual lewat tinker/
                                        seeder bila perlu). Tabel
                                        `password_reset_tokens` sudah
                                        tersedia bila ingin diaktifkan
                                        belakangan.

Rekomendasi awal (dinilai dari audit): SEMUA rekomendasi di prompt SESUAI
dan LAYAK diikuti — satu tabel users, guard web, middleware auth + admin,
satu role admin di fase pertama, login hanya lewat /admin/login (tidak
ditautkan dari halaman publik mana pun).

15. KLASIFIKASI KONTEN LENGKAP (TUGAS 9)
======================================================================

A. Konten global      → tabel `site_settings` (key-value), media
                         direferensikan via `media` table.
B. Konten halaman      → tabel `pages` (meta_title, meta_description,
                         status draft/published, slug/route_name readonly).
C. Konten section      → `page_sections.content` (JSON), 1 baris per
                         section per halaman (25 baris data untuk 25
                         section + section_key unik).
D. Konten berulang      → SEBAGIAN di dalam JSON page_sections (repeater
                         terkunci jumlah, mis. steps/tiles/milestones),
                         SEBAGIAN di tabel khusus untuk yang benar2 bebas
                         tambah/hapus/urutkan tanpa batas kaku: `faqs`
                         (FAQ about-contact), `partners` (logo partner).
E. Data khusus          → `simulation_settings` (data simulasi terpisah
                         dari CMS umum, lihat Bagian 27), `contact_messages`
                         (pesan form, belum aktif), status draft/publish
                         → kolom pada `pages`/`page_sections` itu sendiri
                         (bukan tabel terpisah, lihat Bagian 20).

20. DAFTAR FORM REQUEST YANG DIRENCANAKAN (TUGAS 13)
======================================================================

Ringkasan pola validasi umum yang berlaku di SEMUA Form Request admin:
- Sanitasi: `strip_tags()`/tidak menerima tag HTML pada field string/
  textarea (WAJIB — tidak ada editor rich-text bebas sesuai batasan
  proyek).
- Risiko XSS: dicegah dengan (a) tidak menyimpan HTML mentah, (b) Blade
  tetap memakai `{{ }}` (escaped output) saat render, bukan `{!! !!}`.
- Risiko URL berbahaya: seluruh field url divalidasi `url` + custom rule
  menolak skema `javascript:` dan `data:` secara eksplisit (regex/rule

  bisa meloloskan skema tak terduga tergantung konfigurasi).

22. RENCANA MIDDLEWARE DAN AUTHORIZATION (TUGAS 15)
======================================================================

Middleware yang direkomendasikan:
1. `auth` (bawaan Laravel) — pastikan user login untuk seluruh route
   /admin/* KECUALI /admin/login.
2. `admin` (CUSTOM, belum dibuat) — pastikan `auth()->user()->role ===
   'admin'` (atau via Gate/Policy), diterapkan setelah `auth`.
3. `active` (CUSTOM, belum dibuat, atau digabung ke dalam middleware
   `admin`) — pastikan `is_active = true`; user nonaktif otomatis
   di-logout/ditolak meski sesi masih valid.
4. `throttle` (bawaan Laravel) — rate limit login, mis.
   `throttle:5,1` (5 percobaan per menit) khusus route POST
   /admin/login.
5. `verified` — TIDAK diperlukan fase pertama (tidak ada alur verifikasi
   email admin yang direncanakan; akun admin dibuat manual/seeder).
6. Preview access — bisa berupa middleware tambahan `admin` yang sama
   (preview tetap wajib login, TIDAK memakai token publik terpisah —
   lihat Tugas 20) atau ditegakkan langsung di
   `Admin\PreviewController` via `$this->authorize()`.

Authorization (Policy/Gate) yang dievaluasi:
7. Policy Media — cek kepemilikan/izin sebelum update/hapus (fase 1
   dengan 1 role admin: SEMUA admin punya akses penuh, policy cukup
   sederhana `true` untuk role admin — kompleksitas granular ditunda
   ke fase role>1).
8. Policy PageSection — cek `section_key` yang diedit sesuai endpoint
   (mencegah IDOR lintas section/halaman), bukan soal kepemilikan user.
9. Policy SiteSetting — admin only, tidak granular di fase 1.
10. Policy ContactMessage — admin only untuk read/update status.
11. Policy Publish — admin only di fase 1; disiapkan agar mudah
    diperluas ke role "editor vs publisher" di fase lanjut tanpa
    migrasi ulang struktur.

Kesimpulan: SATU ROLE ADMIN CUKUP untuk tahap pertama. Middleware
`auth` + `admin` (+ pengecekan `is_active`) sudah memadai; Policy
granular per-resource disiapkan strukturnya tapi isinya sederhana
("izinkan semua admin") sampai ada kebutuhan multi-role nyata.

24. STRATEGI INTEGRASI FRONT-END DAN BACKEND (TUGAS 16 & 17)
======================================================================

Prinsip inti: file section Blade, CSS, JS TETAP DIPAKAI APA ADANYA.
Hanya SUMBER data yang berubah — dari teks statis di Blade menjadi
`data_get($section, 'content.field', $fallbackStatisSaatIni)`.

Contoh pola konversi (ilustrasi, BELUM diterapkan):

Sebelum:
  <h1 class="ca-hero__title ca-display">
      Mobil Bekerja.<br>
      Aset <span class="ca-hero__title-accent">Bertumbuh.</span>
  </h1>

Sesudah (konsep):
  <h1 class="ca-hero__title ca-display">
      {{ data_get($hero, 'content.title_line_1', 'Mobil Bekerja.') }}<br>
      Aset <span class="ca-hero__title-accent">
          {{ data_get($hero, 'content.title_line_2', 'Bertumbuh.') }}
      </span>
  </h1>

Standar fallback per tipe field:
- string/textarea → fallback = teks statis yang SEKARANG ada di Blade
  (bukan string kosong, bukan "Lorem ipsum").
- image → jika `content.image` kosong/media terhapus, PAKAI gambar
  statis yang sekarang ada di public/assets/images/* sebagai fallback
  (BUKAN broken image, konsisten dengan aturan front-end sebelumnya).
- alt text → fallback = alt text statis yang sekarang ada (termasuk alt
  kosong "" untuk gambar dekoratif — kekosongan ini SAH, bukan bug).
- link/CTA → jika `route_name`/`anchor` kosong atau tidak valid,
  fallback = tujuan default section itu SEKARANG (bukan `href="#"`).
- list/repeater → jika kosong, fallback = daftar default sekarang;
  TIDAK BOLEH menampilkan daftar kosong tanpa isi (merusak layout
  grid/flex yang mengasumsikan N item tetap pada repeater terkunci).
- boolean (is_active section) → section HANYA disembunyikan
  (`@if($section['is_active'] ?? true)`) bila field ini eksplisit
  false; default TETAP TAMPIL bila kolom belum ada/null (fail-safe:
  konten publik tidak boleh hilang karena data belum lengkap).
- numeric/currency (khusus Simulasi) → lihat Bagian 27, TIDAK PERNAH
  null menjadi 0/Rp0.
- FAQ/partner/simulation → diambil dari tabel khusus (bukan
  page_sections), tetap disediakan Collection kosong yang aman
  di-@foreach tanpa error bila datanya nol baris.

Strategi status:
- section inactive → section disembunyikan TOTAL dari halaman publik
  (bukan ditampilkan kosong) — TAPI perlu dipastikan section yang
  desainnya "berpasangan" (mis. checkpoint 4 tahap ↔ accordion 5 item)
  tidak dinonaktifkan sebagian yang merusak makna alur; disarankan
  toggle is_active hanya di level SECTION PENUH, bukan sub-item
  repeater terkunci.
- draft vs published → controller publik SELALU membaca versi
  `published` (never draft) — draft HANYA terlihat lewat
  Admin\PreviewController yang wajib login.
- preview admin → memakai layout PUBLIK yang sama persis (reuse Blade)
  namun data diambil dari `draft_content`, dan HARUS diberi
  `<meta name="robots" content="noindex">` otomatis (lihat Bagian 28).

Urutan integrasi (WAJIB berpasangan sesuai prinsip yang sudah dikunci):
Editor Admin → Database → Content Service → Controller Publik → Blade
Publik → Pengujian, dikerjakan SATU HALAMAN PENUH sebelum lanjut ke
halaman berikutnya (Home dulu, baru Bisnis, dst. — sesuai urutan
PROMPT 12 tahap 6–10). Selama halaman lain belum terintegrasi, halaman
tsb TETAP memakai konten statis apa adanya (tidak ada halaman yang
"setengah dinamis setengah statis" dalam satu waktu, kecuali di dalam
proses migrasi 1 halaman itu sendiri).

Strategi Link & CTA (Tugas 17):
Field CTA disimpan TERSTRUKTUR, bukan string href bebas:
  { "label": string, "type": "internal"|"external"|"anchor",
    "route_name": string|null, "anchor": string|null,
    "external_url": string|null, "target": "_self"|"_blank",
    "rel": string|null, "is_active": boolean }
Validasi:
- type=internal → route_name WAJIB ada di whitelist 5 nama route resmi
  (home/business/partnership/simulation/about-contact); resolusi akhir
  URL selalu lewat `route($route_name)` di Blade (bukan menyimpan URL
  mentah), sehingga jika route berubah, seluruh CTA otomatis ikut benar.
- anchor → WAJIB dari whitelist anchor yang benar2 ada di desain saat
  ini (mis. #contact, #cara-kerja, #operate, #mitra-owner, #mitra-driver,
  #dasar-perhitungan, #simulasi-satu-unit, dsb.) — bukan bebas ketik.
- type=external → external_url WAJIB lolos validasi `url`, DITOLAK bila
  berawalan `javascript:` atau `data:` (custom rule eksplisit,
  bukan hanya mengandalkan validator `url` bawaan).
- target=_blank → rel WAJIB otomatis diisi sistem `noopener noreferrer`
  (tidak diserahkan ke input admin agar tidak lupa/salah ketik).

25. STRATEGI MEDIA LIBRARY (TUGAS 19)
======================================================================

Format diizinkan: JPG, JPEG, PNG, WebP. SVG TIDAK diizinkan di fase
pertama (SVG bisa membawa script/XSS bila tidak disanitasi ketat —
ditunda sampai ada kebutuhan nyata + sanitizer khusus, mis.
`enshrined/svg-sanitize`, BELUM diinstal sekarang).

php.ini 2GB bawaan dev — WAJIB diatur eksplisit di StoreMediaRequest,
jangan mengandalkan php.ini).
Nama file: DIHASILKAN SISTEM (uuid/hash + ekstensi asli tervalidasi),
`original_name` tetap disimpan sebagai metadata terpisah untuk
ditampilkan ke admin.
Metadata yang disimpan: original_name, mime_type (dari isi file, bukan
ekstensi saja — Laravel `mimes` rule sudah menangani ini via fileinfo),
size, width, height (dibaca via `getimagesize()`/GD saat upload),
alt_text, caption, uploaded_by.
Cek penggunaan sebelum delete: query sederhana ke `page_sections.content`
(LIKE pada JSON, atau field terstruktur bila media_id disimpan sebagai
angka jelas di JSON) + tabel `partners`/`site_settings` — jika masih
dipakai, tombol hapus DINONAKTIFKAN/beri peringatan, bukan langsung
hard delete.
Disk: `public` (storage/app/public → public/storage via symlink, BELUM
dibuat pada tahap audit ini).
Tidak menyimpan file executable: validasi MIME + ekstensi ganda (mis.
tolak `.php.jpg` dengan mengecek ekstensi asli TERAKHIR saja dan
mime_type asli).
Tidak menimpa file lama dengan nama sama: nama file sistem selalu unik
(uuid), jadi secara desain TIDAK MUNGKIN menimpa.
Crop manual: BELUM diperlukan di fase pertama (seluruh gambar saat ini
sudah di-crop manual lewat proses PHP GD selama pembangunan front-end;
admin fase 1 cukup upload+pilih+ganti+alt+hapus, tanpa editor crop
interaktif — sesuai prioritas "Tugas 19" yang membatasi ke 6 fungsi
dasar itu).

27. STRATEGI DRAFT, PREVIEW, DAN PUBLISH (TUGAS 20)
======================================================================

Rekomendasi: PENDEKATAN A (draft_content + published_content pada
page_sections) DIGABUNG dengan content_revisions sebagai HISTORI
(bukan mekanisme utama baca/tulis). Alasan: pendekatan A jauh lebih
sederhana untuk 25 section yang jumlahnya tetap (tidak butuh versioning
kompleks ala Git), sementara `content_revisions` tetap disediakan
sebagai log/riwayat agar admin bisa melihat "apa yang berubah kapan"
dan (di fase lanjut) rollback manual dengan menyalin isi revisi lama
kembali ke `content`.

Struktur data: page_sections.content (published, dibaca publik) +
page_sections.draft_content (nullable, dibaca HANYA saat preview admin)
+ page_sections.status (draft/published) + published_at + published_by.
Setiap kali `publish()` dipanggil: content_revisions dibuat dari isi
`content` LAMA (sebelum ditimpa) sebagai snapshot histori, lalu
`draft_content` disalin ke `content`, `draft_content` dikosongkan,
`published_at`/`published_by` diperbarui.

Route preview: /admin/pages/{page}/preview — TIDAK memakai token publik
yang bisa ditebak; akses SEPENUHNYA lewat sesi login admin (middleware
auth+admin), BUKAN token URL semi-publik. Ini menjawab syarat "preview
tidak boleh dapat ditebak publik" dengan cara PALING AMAN: preview
tidak pernah bisa diakses tanpa login sama sekali, sehingga tidak ada
token untuk ditebak.
Preview tidak boleh terindeks: response preview WAJIB menyertakan
header/meta `noindex` (baik lewat `X-Robots-Tag: noindex` header HTTP
maupun meta tag di layout khusus preview) — detail implementasi
ditentukan saat pembangunan, bukan sekarang.

Rollback: cukup MANUAL di fase 1 (admin melihat isi
`content_revisions.content` lama, lalu admin menyalinnya kembali via
form edit biasa) — TIDAK perlu fitur rollback otomatis 1-klik di fase
pertama (kompleksitas tidak sepadan dengan manfaat di skala 25 section
+ admin sedikit).

Caching: ContentService WAJIB invalidate cache page/section terkait
SETIAP kali publish() dipanggil (bukan hanya saat save draft) — agar
publik langsung melihat versi baru.

Risiko: draft tampil ke publik BILA controller publik salah membaca
`draft_content` alih-alih `content` — WAJIB test eksplisit
"draft tidak tampil publik" (lihat Bagian 30 rencana pengujian).

   membuat ulang tabel users.

4. Sepakati storage:link akan dijalankan di Tahap 5 (Media Library),
   bukan sebelumnya.

   MASIH placeholder — `whatsapp_link_mode` sebaiknya default "anchor"
   sampai nomor resmi dikonfirmasi valid.
